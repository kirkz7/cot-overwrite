智能体记忆：按时间排的脉络

2026-11-12 第一版。按导师的建议整理：每个阶段当时的问题是什么、怎么修的、修完又留下什么问题。重点是编程智能体。
年份和月份按 arXiv 编号。2026 年 6 月以后的论文都读过（深浅见 阅读笔记_智能体记忆.md）；2025 年以前的几篇是凭已有了解写的，这一轮没有重新核对，标了 †。

一条线贯穿下来：每一轮修法都解决了"记不住"或者"装不下"，同时制造了一份新的、会过时的东西。先是外存的记忆，然后是指令文件和压缩摘要，现在是从这些东西再派生出来的索引、计划和结论。

一、时间线

第一阶段（2023–2024）：先解决"装不下"

当时的问题对话和任务历史超过上下文窗口。编程智能体每个任务从零开始。
怎么修的把历史放到上下文外面，用的时候取回来：分页式的虚拟上下文（MemGPT †）、记忆流加反思（Generative Agents †、Reflexion †）、技能库（Voyager †）。编程智能体这边是单任务内的工具循环（SWE-agent †、OpenHands †）。
留下的问题记忆被当成"存进去、取出来"。存进去的东西以后还对不对，没有人管。

第二阶段（2025）：记忆变成产品，指令文件成为标准

当时的问题原始历史太长太乱，取回来的东西质量差；每次会话都要重新告诉智能体项目的规矩。
怎么修的写入时整理：抽事实并做增删改（Mem0 †）、时间知识图谱（Zep / Graphiti †）、互相链接的笔记（A-Mem †）、记忆操作系统（MemOS †）。编程智能体这边出现两样东西：仓库里的指令文件（CLAUDE.md、AGENTS.md），每次会话自动载入；上下文快满时自动压缩成摘要。年底有了对指令文件的实证研究（2511.12884）。
留下的问题现在有三份会过时的东西：整理过的记忆、指令文件、压缩摘要。它们都是从原始信息改写来的，改写时会丢东西，原始信息变了它们也不会自己跟着变。

第三阶段（2026 年 1–6 月）：开始量，发现问题

当时的问题这些记忆到底有没有用、什么时候会坏，没有数据。
量了什么
  • 指令文件对任务成功率的帮助不稳定，但智能体会照着做（2601.20404、2602.11988）。
  • SWE-chat（2604）：第一份真实开发者使用编程智能体的会话数据。用户在 46% 的轮次里反驳智能体。
  • STALE、MEME（2605）：把"记忆过时"和"依赖更新"做成基准，现有系统接近零分。
  • Context Rot（2606）：356 个仓库里 23% 的指令文件有过时的代码引用。
  • 把智能体记忆当数据管理系统来评测（2606.24775）。
留下的问题问题被命名了：过时、失效传播、压缩丢信息。但都只是诊断，没有修法；而且多数数据是合成的。

第四阶段（2026 年 7–11 月）：一批修法，按"在哪一步修"分成四类

在哪一步修代表工作做法修好了什么没修的
写入时
记下来历和依赖		MemTX（2607）、StateMem（2608）、Stashbird（2609）、Tether、PACMI（2610）、StateGraph（2611）每条记忆记下它依据什么；上游失效时由程序撤回或标记下游依赖明说、或由智能体声明时，传播可以不靠模型（Tether：62% → 0.3%）没有明说、要推断的依赖；写入者弱时漏记变化
运行时
把上下文和来源挂钩		Invalidation Contracts（2609）、Concord、MemTrace（2610）工具读到的内容登记来源；来源一变（哈希、版本戳），原地改掉或拿掉文件、接口这类可以机器观察的直接过时（Concord：40/40）由这些内容派生出来的摘要、计划、决定
使用前
核查再行动		Stale Constraints（2608，诊断）、TRACE、PLANFENCE（2609）、StateWise（2610）动作或回归之前，找出依据的记录，核实，修好再做单条记录被改坏时的恢复（StateWise：39% → 93%）每次都要用强模型核查，成本高；互相影响的多条记录
训练AutoCompact、Accept Changes（2610）训练智能体何时压缩、保留什么；微调小的记忆管理器压缩时机；事实本身的变化（含暗示的）依赖传播；派生内容

同一时期的诊断，说明问题比想的更深：

  • 顶级模型从长历史里重建状态很差，把算好的状态给它就全对（When Context Changes，2609：18/40 对 40/40）。
  • 记忆系统在"派生状态"上全部低于关键词检索，隐式变化只刷新 41%（MemDerive，2610）。
  • 真实仓库历史上，记忆能救回一些任务，也让 5–10% 原本能做的任务变坏（MemDev-Bench，2610）。
  • 过时的指令被照做，成功率看不出来，智能体从不去修（2610.30571、2611.09802）。
  • 压缩之后规则还在，违规却多了 2.6 倍（ARCBench，2611）。
  • 接手真实项目时，六种顶级配置还原需求状态 0/312（Take It From Here，2611）。
  • 删除：没有系统端到端通过超过 1.5% 的遗忘请求（Bemula，2610）；删了原始记录，派生的摘要里还问得出来（AfterDeleteBench，2610）。

二、把修法和问题对起来看

会过时的东西它从哪来现有的修法还缺什么
上下文里的工具观察读文件、查接口Concord、MemTrace：挂钩来源，原地改基本有解（来源可观察时）
缓存的结论和核验结果智能体自己算的Tether、Invalidation Contracts：记依据，程序撤回依据没明说时
指令文件（CLAUDE.md 等）人写，或智能体写检测过时的代码引用；加一句"以代码为准"只能查路径、命令这类可机器核对的；规矩和约定查不了；没人自动修
压缩摘要从对话历史压缩AutoCompact：训练压缩策略摘要里的内容之后过时了怎么办，没人做
智能体自己写的记忆笔记从会话里提炼StateWise：用之前核查笔记之间的依赖；便宜的维护办法
从记忆再派生出来的东西
索引、摘要的摘要、计划、任务优先级		从上面几样再加工Concord 明说留作以后；AfterDeleteBench 只管删除几乎空白。连它有多常过时都没人量过

三、现在的问题，归成五条

  1. 派生内容过时。修法都停在"第一层"：原始信息变了，直接依赖它的那条能被处理；再往下派生一层的东西（索引里的一句描述、压缩摘要里的一个结论、据此定的计划）没人管。
  2. 没有明说的依赖。现有修法要求依赖被说出来或被声明。真实笔记里的依赖多数不明说。
  3. 瓶颈是"发现"，不是"推理"。该查的不去查；提醒了也不重读；顺口提到的变化被漏记。
  4. 维护的成本。用强模型逐次核查很贵；让模型维护完整状态又做不对（0/312）。便宜的、只做一小件事的维护没人系统试过。
  5. 真实数据太少。修法几乎都在合成数据上验证。真实数据上只有三个数字：23% 的仓库（指令文件）、100 段会话里 40 条失效链（StateWise）、我们数的笔记变化里 17% 是依赖事件。

四、可能的新点（我的想法，待讨论）

候选：真实智能体记忆里的"派生内容过时"。
  • 为什么可能是新的：第二部分那张表的最后一行。四类修法都没有覆盖，Concord 把它写进了"以后的工作"。
  • 为什么能做：Claude Code 的记忆天然有派生结构（MEMORY.md 的每一行是对一条笔记的描述），而且有真实数据。手头 53 个仓库里已经能配出 236 组"索引行对笔记"；SWE-chat 全量有约 1.8 万段会话。
  • 已有的苗头：我们确认的三例"下游留旧"里，有一例就是笔记写了"已发布"、索引还写"进行中"，之后被读了两次。
  • 可以怎么展开：先量（多常见、哪类笔记、过多久），再看后果（智能体读到过时索引后有没有照做，用户有没有纠正），最后才是修法。这个顺序本身回应了"工程思维太重"的意见。
  • 风险：还没数，可能很罕见；样本是早期用户；只有 Claude Code 一种记忆结构。
