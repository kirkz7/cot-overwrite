## 4. StateWise（2610.05241，浙大等，2026-10-04）

**读了**：摘要、引言、相关工作、问题定义的开头、审计那张图、全部六个实验问题的结果、讨论。**没读**：方法 4.1–4.4 的细节、指标的精确定义、参考文献。成本数字（模型调用数、token）论文里有指标定义，我读到的部分没有看到具体数。

**做了什么**
- 问题：编程智能体跨任务保留的"操作记录"（环境事实、仓库策略、开发者意图）会过时。现有做法只拦动作，不修记录，下次还会错。
- 方法：在有副作用的动作执行前，(1) 用"逐条记录的反事实重新规划"找出决定这次动作的记录；(2) 分层核实它现在是否有效（可机器核实的去读环境，属于开发者意图的去问）；(3) 把更正写回持久记忆并保留来历；(4) 重新规划，再独立检查一次。

**对真实数据的审计（和我们想做的事重合）**
- 从 SWE-chat 抽了 **100 段会话**，模型标注出 60 条候选"失效链"（早先的操作事实 → 后来依赖它的动作 → 有相反的证据 → 可见的后果），核对引用的轮次和时间顺序后留下 **40 条**。
- 40 条里的后果：任务失败 17，用户出手纠正 15，不安全的修改 6。记录失效的原因（可重叠）：和新证据冲突 30，用错了范围 25，没有从当前环境核实 25，过时 17。来源：Claude Code 28，OpenCode 12。
- 它自己写的限制：审计靠模型标注，主要覆盖一个智能体家族。

**实验**
- 基准：150 个可执行的编程智能体案例（自建），每例只改坏一条目标记录。
- 只改坏一条记录：整体正确率 80.7% → 38.7%，不安全动作 0% → 42.7%。把那条记录删掉只回到 45.3%。StateWise 93.3%，没有不安全动作。
- 提醒智能体"先看看当前环境再做"（Live Refresh）：150 例里 105 例去看了，正确率只有 42.0%。
- 更正写回后，后面三个任务的正确率 92.7%，和记录本来就对的时候（91.7%）一样。
- **模型**：主规划器 GPT-5.6-sol；另测 DeepSeek v4 Pro、Qwen 3.7 Max、Claude Fable 5（20 例），正确率 80.0%–94.4%。**全是强模型，没有便宜模型。**

**和我们的关系**
- 它已经在 SWE-chat 上做了一次"过时状态导致失败"的人工加模型审计，100 段里 40 条。我们计划的"真实数据里多常见"不再是完全没人做的，但它量的是"失效链"，没有区分"直接过时"和"因为上游变了而过时"（依赖），也没有报占全部会话或全部纠正的比例口径（100 段是怎么抽的我没读到）。
- 它的方法是**读取 / 动作时**的修复，每个有副作用的动作前都要做反事实重新规划，成本不低，而且用的是强模型。它没有问"维护者能不能便宜"。
- 它的设定里过时是单条记录被改坏，不涉及依赖传播。

## 5. Tether：Memories That Outlive Their Reasons（2610.25123，南昆士兰大学等，2026-10-18）

**读了**：摘要、引言前半、问题定义、方法、基准设计、实验设置、6.5（其他模型、窗口、边的噪声）、6.6（依赖和结论不在同一会话）、相关工作、限制、结论。**没读**：6.1–6.4 的正文（主结果只从摘要和后文引用得知）、附录。

**做了什么**
- 场景：智能体在 Web 上发布软件包、模型、数据集。发布前要核验，记住"核验过了"可以省核验次数。但结论依赖前提：签名密钥被吊销后，建立在它上面的东西都不再通过，而公告只提那把密钥。
- 关键观察（"失效是非局部的，推导是局部的"）：下游的旧结论和上游的失效公告往往不会出现在同一个检索窗口里，所以**读者再聪明也没用，证据不在它面前**；但结论是在哪些前提上得出的，在写入那一刻是看得见的。
- 方法 Tether：在原子事实记忆上只加一个字段。写入时，给每条"核验结论"记下它依据的确切版本（`derived_from`）。读取时，用一次不调用模型的可达性计算，把任何上游已失效的结论改成"未确定"再给智能体看。智能体看到的字段和原来一样，看不到边。
- 基准 Fallout：合成的带版本的世界（链、菱形、树、中心辐射等拓扑），三个领域，历史对话由一个不带记忆的智能体录一次，所有记忆方法共用。

**主要数字**
- 原子事实记忆（没有边）：上游失效的对象有 62% 被照常发布，每一条依据的记录在写入时都是对的。
- Tether：0.3%，核验次数比"全部重查"少 37%。
- A-Mem、Graphiti：9%，但它们几乎每个候选都重查（0.83–0.86 次），省不了多少；Mem0：42%。
- "任何失效都清空全部结论"和 Tether 一样安全，但多 32% 的核验。
- 把整个记忆库都给写入者和读者看，无边的记忆也只降到 25%，上下文长 8 倍。

**和"便宜写入者"直接相关的结果（6.5、6.6）**
- 所有角色（用户模拟、写入者、读者智能体）用**同一个模型**：主实验 gpt-6-luna（关推理）。换成开源模型时，也是同一个模型既当写入者又当智能体。
- Qwen3.5-35B-A3B 当写入者：边的召回 0.931；用户顺口提到的失效有 **22% 没被记下**（gpt-6-luna 是 1.7%）；上游失效对象的误发布率 30%（无边的记忆 78%）。Qwen3.5-27B：11%（无边 84%）。DeepSeek-V4.1-Flash：边召回 99.5%，误发布 0.6%。
- 写入者弱到一定程度，Tether 反而比"几乎全部重查"的基线更不安全。
- 依赖关系和结论不在同一个会话里说：边召回从 1.000 掉到 0.840（关系先说）和 0.658（关系后说），误发布率从 0.6% 升到 9.4% 和 22.1%。
- 读取时随机丢边：丢 5% / 10% / 20%，误发布 5.8% / 10.5% / 21.2%，基本成正比。

**它自己承认没做的**
- 依赖关系都是**明说**在粘贴的记录里的；"需要写入者自己推断的依赖没有测"。
- 世界是合成的。
- "Tether 依赖有能力的写入者"。

**和我们的关系（重要）**
- 这基本就是我们说的"依赖账"：原文（原子事实）照存，写入时多记一层"谁依赖谁"，读取时由程序而不是模型来处理过时。它已经做出来了，而且报了便宜写入者会掉多少。**"给读取派加一本依赖账"这个想法本身不再新。**
- 它和我们设想的差别：
  1. 它的记忆内容是"通过 / 不通过"的核验结论，处理方式是撤回成"未确定"。没有 MEME 级联题那种"按规则算出新值"，也没有区分"有规则可算"和"没有新值该说不知道"。
  2. 所有角色同一个模型。**没有"主模型强、维护者便宜"的分工**，也没有问维护者可以便宜到什么程度（只是整体换成小模型）。
  3. 依赖都是明说的。我们在真实笔记里看到的依赖多数是不明说的（部署目标和健康检查地址的关系没有人写"取决于"）。
  4. 合成数据。
- 它的结果给了我们一个可以引用的先验：35B 级的写入者，明说的依赖能认出 93%，但会漏掉 22% 顺口提到的失效事件。**漏的主要不是依赖，而是"变化发生了"这件事。**

## 读完 5 篇后的判断（旧，已被文末"读完 9 篇后的判断"取代）

- **"依赖账"作为机制已经有人做了**（Tether；StateGraph、PACMI 也是这一类）。再做一个机制，新颖性不够。
- **"维护者可以便宜到什么程度"还没有人正面回答。** Tether 只是把所有角色一起换成小模型，StateWise 全用强模型。强主模型加便宜维护者的分工、以及便宜到哪一级开始失效，目前读到的 5 篇里没有。
- **"不明说的依赖"没有人测。** Tether 明确写了没测。真实数据（我们数的笔记、StateWise 审计的会话）里的依赖大多不明说。
- **真实数据的普遍性有人开了头**（StateWise 的 100 段审计，40 条失效链），但没有按"依赖"来分，也只是模型标注。
- 待读的里面最可能推翻上面判断的：Fresh Memory Stale Plans、MemTX、TRACE、Stashbird、Explicit Belief States。

## 6. Fresh Memory, Stale Plans / PLANFENCE（2609.03340，普渡等，2026-09-03）

**读了**：只有检索工具给的一份自动生成的摘要报告，**没有读论文原文**。下面的内容可信度比其他几篇低。

- 场景：分布式多智能体。一个执行者手里的共享状态是最新的，但它要执行的计划是按旧状态推出来的（"状态新鲜"不等于"计划有效"）。
- 方法：每个派生记录写明它依据的确切版本；每个动作的工具封装**事先声明**它依赖哪些键；动作前只核对这些键是不是还是当初的版本，不是就重新规划一次。
- 结果：只看状态新不新的做法，330 个任务全部按过时计划执行；核对来历的做法全部正确。其余是系统开销的比较（更新频繁时动作前核对更省，更新少时主动同步更省）。用的是 5 个 Qwen3.5 智能体。
- 它自己承认没做的：**依赖要靠声明，不处理需要推断的依赖**。
- 和我们的关系：结构上是同一个想法（记下来历，用之前核对），但它是系统和一致性方向的论文，依赖是程序员声明的。和我们关心的"从对话里认出依赖"不重合。

## 7. When Context Changes: Understanding Update Failures in LLMs（2609.38866，伯克利，2026-09-30，v2 10-29）

**读了**：摘要、引言、第 2 节（现象）、第 3 节开头（基准）、第 6 节后半（测试时干预的结果表）、相关工作。**没读**：第 4 节机制分析和第 5 节理论的正文、限制一节（输出被截断）、附录。

**做了什么**
- 把"同一个变量被多次更新后，模型答成旧值"叫作"过时绑定"。更新历史全部在上下文里，不涉及检索。
- 基准 CICM：对话里的偏好更新 1200 段，外加决策题和 2048 步操作日志（每一步依赖前面的交接）。
- 机制：探针能从模型内部读出新值，但回答时注意力偏向旧值（"注意力漂移"）。用单层 transformer 给了一个解释：几个旧值合起来分到的注意力可以超过新值。
- 修法：不训练，测试时把选定注意力头的注意力往新值上偏。小模型上准确率大幅提高（例如 Qwen2.5-3B 16% → 95%，Llama-3.1-8B 42% → 89%），原本答对的基本不受影响。

**对我们最有用的数字**
- **顶级模型在长而复杂的更新历史上也不行**：2048 步的仓库和发布日志，历史完整、规则明说，GPT-5.6 Sol 答对 9 / 40，Claude Opus 4.8 答对 18 / 40。**同样的题，把算好的当前状态直接给它们，40 / 40 全对。**论文的原话意思是：难的是顺着历史把状态重建出来，不是读状态。
- 小模型不改写时没问题，被改写的次数越多越差；333 次错误里 331 次答的是同一个变量的旧值。
- 选择题会把这个错误藏起来：准确率差不多，但自由作答的错误里 82% 是旧值，选择题只有 29%。

**和我们的关系**
- **和上一个项目（cot-overwrite）几乎是同一个现象**，而且它做了机制、理论和一个免训练的修法。这印证了导师"上一个题目太小"的判断：那块地方现在已经有一篇做得比较完整的工作。
- 对新题目：它给了"即使是顶级模型，也应该有人把当前状态维护好再给它"的直接证据（40 / 40 对 9–18 / 40）。这正好回应"换到用顶级模型的场景，是不是只剩删除"的疑问：不是。
- 它只管"同一个变量的新旧值"，不管"上游变了导致下游失效"。

## 8. When Agent Context Goes Stale / Concord（2610.05281，港大，2026-10-04）

**读了**：全文（正文 6 页加参考文献）。

**做了什么**
- 问题：智能体把工具读到的内容（比如文件内容）留在上下文里，之后文件被别人改了，上下文里的旧内容还被当成事实用。
- 方法 Concord：在运行时和外部资源之间加一层。每条工具观察登记成"带来源的上下文块"；来源一变（用文件哈希和写入钩子发现，**不调用模型**），就找到所有受影响的块，按策略处理：小改动直接把块的内容原地改成新的；大改动就把块从提示里拿掉，并强制重新读。
- 基准：从 HotpotQA 改的 40 题，先让智能体读到被改过的证据，再把文件改回去。

**主要数字**（40 题里答对几题）

| | Claude Sonnet 5 | GLM 5.2 | DeepSeek V4 Pro |
|---|---|---|---|
| 什么都不做 | 20 | 15 | 24 |
| 追加一句"某路径被修改了" | 26 | 23 | 31 |
| 给一个看差异的工具，并强制看过才能答 | 36 | 31 | 38 |
| Concord（原地改或拿掉） | 40 | 40 | 40 |

- 追加提醒只有在它引发了重新读文件时才有用（17 / 18 对）；提醒了但没重读，只有 2 / 8 对。

**它自己承认没做的**
- **不处理由过时观察派生出来的摘要、计划、决定。**原话意思是：追踪这类派生内容是否还有效更难，需要更丰富的依赖建模，留给以后。
- 只测了本地文件、40 题、人为构造的竞争条件。

**和我们的关系**
- **"只加一行提醒不够，要把条目本身改掉"**这个结论，它在顶级模型上量到了（提醒 26 / 40，原地改 40 / 40）。我们在 8B 上的阶梯是同一个结论（标记行 +4 到 +6 点，改写 +59 点）。两头对上了，这是可以引用的互证。
- 对"直接过时"且来源可以机器观察的情况，维护者可以便宜到不用模型。所以"维护者能便宜到什么程度"这个问题要限定在**派生内容和不明说的依赖**上才有意义，而这正是它留下的空白。

## 9. Take It From Here: Evaluating Coding Agents on Project Takeover（2611.07307，Upwork、悉尼科技大学等，2026-11-05）

**读了**：摘要、引言、数据构造、实验设计的开头、5.2（需求理解的结果）、限制、结论。**没读**：相关工作、3.1–3.2 的任务和诊断定义细节、5.1 和 5.3 的正文、第 6 节、附录。

**做了什么**
- 任务：让编程智能体中途接手一个进行中的项目。给它完整的交互历史、当前请求和项目环境，要它完成请求。
- 数据：**44 个真实的长期协作项目**（软件、文档、电路板设计），历史 18 到 1075 轮，平均 181 轮。人工标注"需求原子"和每次变更，四名审核人两两复核。349 个诊断目标，其中 37 个能做可执行验证。
- 模型：GPT-6 Astra、GPT-6 Sol、GPT-5.6 Sol、GPT-5.6 Terra（Codex CLI），Claude Opus 5.5、Claude Sonnet 5（Claude Code），都用高推理强度。**全是顶级模型。**

**主要数字**
- 完整交付率：给全部历史 4.95%；只给相关历史（平均 8.7 轮）2.70%，没有变好。
- **从历史里重建"请求之后的需求状态"，六种配置完全正确的是 0 / 312。**最好的 Opus 5.5 部分得分 0.17。
- 重建请求之前的状态：能找到 50–68% 的需求，但具体属性的重建分只有 0.24–0.28。
- 证据检索：召回 0.67–0.92，精确率只有 0.23–0.43。
- 更新时会把自己刚刚还原出来、而且仍然有效的约束丢掉（给了一个电路板的例子）。
- 把正确的目标状态直接给它：完整交付率 8.11%，目标测试通过 9.01%。也就是状态对了，实现也还是难。

**和我们的关系**
- 这是目前读到的最强的"顶级模型加真实数据也不行"的证据：真实项目、人工标注、六种顶级配置、0 / 312。
- 它量的是"需求状态"整体（哪些需求现在有效、具体是什么），不专门区分依赖。但"更新时丢掉仍然有效的约束"和"上游变了下游没跟着变"是同一类维护错误的两面。
- 它说明**把状态写对本身就很难，顶级模型也做不到**。这对"维护者可以便宜到什么程度"是个坏消息：如果顶级模型都写不对，便宜模型更写不对。问题可能要改成"维护者只做哪一小部分，才是便宜模型做得了的"。

## 读完 9 篇后的判断（2026-11-11；取代上面"读完 5 篇后的判断"）

**一、"换到用顶级模型的场景，是不是只剩删除"：不是。**现在有三条直接证据，都是顶级模型：
- 长而复杂的更新历史：Opus 4.8 答对 18 / 40，把算好的状态给它是 40 / 40（第 7 篇）。
- 真实项目的需求状态：六种顶级配置 0 / 312 完全正确（第 9 篇）。
- 上下文里的过时观察：Sonnet 5 什么都不做时 20 / 40（第 8 篇）。

**二、"状态要有人维护好再给模型"这个大方向，证据很足。**第 7、8、9 篇和 MemDerive 都指向同一句话：读一个维护好的状态很容易，从历史里重建状态很难，对顶级模型也一样。

**三、但"怎么维护"已经很挤，而且分成了三种做法：**
- 来源可以机器观察的直接过时：不用模型，哈希加钩子就行（Concord）。
- 明说的依赖：写入时记边，读取时由程序撤回（Tether；PLANFENCE 是声明式的版本）。
- 动作前临时诊断和修复：用强模型做反事实重新规划（StateWise）。

**四、还没看到有人做的（比读完 5 篇时更具体了）：**
1. **不明说的依赖**。Tether 和 PLANFENCE 都写明不处理要推断的依赖；Concord 写明不处理派生的摘要、计划、决定。三篇把同一块留作了未来工作。
2. **强主模型加便宜维护者的分工**。没有一篇把两个角色分开用不同档次的模型。
3. **按"依赖"来分的真实数据计数**。StateWise 的审计和第 9 篇的标注都不按依赖分。我们数的那份笔记（依赖事件 17%）是目前唯一按依赖分的，但只是模型单人标注。

**五、一个要正视的坏消息。**第 9 篇显示顶级模型从真实历史里写出正确状态都是 0 / 312。"让便宜模型维护状态"如果指的是维护完整状态，大概率做不到。可行的问法更可能是：**便宜的维护者只做一件很窄的事（比如只认"哪些条目依赖哪些条目"，或者只认"发生了变化"），够不够用。**Tether 的结果给了一个参照：35B 的模型明说的依赖能认出 93%，但顺口提到的变化漏掉 22%，也就是瓶颈可能在"认出变化"而不在"认出依赖"。

**六、一个意外的互证。**"加一行标记不够，要把过时条目本身改写掉"，我们在 8B 上量到（+4 到 +6 点对 +59 点），Concord 在顶级模型上量到（26 / 40 对 40 / 40）。

**还没读的里面，最可能改变上面第四条的**：MemTX、TRACE、Stashbird、Explicit Belief States、MemTrace。

# 第三批到第六批（2026-11-11 晚到 11-12；用户说不用逐批审批，读完为止）

读法说明：从这一批起，除特别注明外，每篇读的是摘要和引言开头、贡献段、用到的模型、限制、结论，没有读方法和结果的全文。可信度低于前两批。

## 10. MemTX（2607.23929，南昆士兰大学等，2026-07）
**读了**：只有一份自动生成的摘要报告，没读原文。
- 主张"写进记忆"和"确认成信念"是两回事。每条记录有八个状态（原始、暂定、已验证、已确认、可据以行动、隔离、被取代、已撤回）。不可逆的动作只有在依据的信念达到"可据以行动"时才放行。撤回一条信念时，沿派生图把下游的信念撤回、把派生的摘要隔离、把已做的工具动作补偿或记为泄漏。
- 自建 90 例的一致性测试加 56 例加难版。模型：Qwen3-8B、Qwen2.5-14B、GLM-4.7-Flash、GPT-5.4-mini、GPT-5.5。**用到了小模型**，但报告里没有给各模型的分数（只有 GPT-5.5 上 0.756）。
- 它自己承认的盲区：**派生关系要靠智能体写入时自己声明**。智能体把私有内容转述进共享摘要却不声明来源时，所有方法（包括它）都失败。原话意思是需要"能跟着内容走到动作那一刻的来历"。
- 关系：级联撤回的协议最完整的一篇，但依赖是声明的。和 Tether 互补（Tether 说它可以消费自己抽出来的边）。

## 11. TRACE（2609.33517，上海交大、MemTensor 等，2026-09-27）
- 场景：多智能体团队里一个成员离开一段时间再回来，它带着的记忆哪些还能用。叫"时间上的记忆准入"。
- 做法：免训练。把离开时的检查点和离开期间的变更对账，处理显式和**隐式**失效（用模型核对），只放行覆盖了它未完成义务的一小份"回归视图"。
- 结果：整份恢复会放进过时内容，整份清空会丢掉有效内容，两者各在一头是 0%。TRACE 两头都高（有效信息可用 93–98%，过时信息拒绝 98–99%）。**收益集中在隐式和传播性的失效上，显式更新上没有稳定优势。**在 STALE 的隐式冲突子集上比最强对比方法高 18–28 点，token 约 2.3 倍。写入时整理的流水线更准，但 token 是它的 4 倍。
- 模型：Qwen3.5-122B、Gemini-3-flash、DeepSeek-v4-flash。中等偏便宜的模型。
- 限制：隐式失效依赖候选覆盖和核对器的校准，"漏掉的依赖会放进过时状态"。离开越久越差：早期 73% 降到后期 43%，token 翻倍。
- 关系：**它处理了不明说的失效**，所以"不明说的依赖没人做"这句话要改：STALE 基准的隐式冲突子集和 TRACE 已经在做，做法是读取时用模型去核对。中等模型在离开较久时只有 43%。

## 12. Explicit Belief States / PoS（2610.01415，南开、阿里等，2026-10-01）
- 推理时构造并持续维护一份显式的"信念状态"（对当前世界的估计加上还没完成的任务要求），检查一致性，发现"原地打转"时做恢复。
- 四个基准（执行类和诊断类，例如 ALFWorld），三个模型（Qwen3.7-Plus、GLM-5.3 等）上都最好。
- 限制：token 和计算成本更高；用自然语言反复改写信念会有冗余、遗漏和语义走样。
- 关系：又一条"显式维护状态优于保留或压缩历史"的证据。维护者就是主模型自己，没有分工，也不专门处理依赖。

## 14. Stashbird（2609.34242，微软，2026-09-28）
**读了**：全文。
- 对话记忆图。每个派生出来的实体和关系都记着它来自哪些原始片段。更新时：重复的证据增加支持，更正会取代旧关系（旧的留作历史）。删除一个片段时：只由它支持的派生记录删掉，还有别的片段支持的保留，受影响的社区摘要从检索里拿掉等待重建。
- 在"语义判断给定"的条件下，20 个更新序列对账后全部正确（不对账 8 个）；263 次删除干预全部通过。四个长期记忆基准上准确率有竞争力，写入的 token 比 Graphiti 少 76 倍。写入和作答用的是 gpt-4o-mini、gpt-4.1-mini 这一档的**便宜模型**。
- 限制：删除片段后，对话摘要和滚动检查点不改；问答评分没有人工验证。
- 关系：它的"来历"是"这条记录来自哪段原文"，不是"这个事实取决于那个事实"。所以它解决删除和直接更正的传播，不涉及依赖更新。聊天场景，便宜写入者。群聊基准上知识更新题只有 36%。

## 16. MemTrace（2610.04838，上海交大、MemTensor 等，2026-10-04）
- 编程智能体做长任务时，把执行历史存成不可变的"记忆轨迹"，锚定在文件、符号、测试上。上下文紧张时只留锚点。恢复历史证据之前，先对照当前仓库状态检查它还有没有效。
- 三个长任务编程基准上都比基线高（例如 DeepSWE pass@1 高 21 点）。
- 关系：和 Concord 同类，针对来源可以机器观察的直接过时。只在单个长任务内，结论里写了跨任务、跨会话是以后的工作。

## 13. When Evidence Changes（2610.03902，奥尔巴尼大学，单作者，2026-10-02）
- 问题：智能体从文档里抽出的派生事实，在文档被撤回或替换之后，是修记忆划算，还是直接重读当前证据划算。
- 数据：公开的重症监护病历（真实数据），用药清单和问题清单任务。模型：**两个 7B 小模型**（Qwen2.5-7B、Mistral-7B），外加一个 32B 的补充。成本把写入、修订、每次使用都算进去。
- 结果：短记录上，任何记忆流水线的总成本都至少是"每次重读全文"的两倍。把记录加长到约 1 万 token 后，记忆在用了 2–14 次之后才比重读全文便宜，但"只重读相关来源"始终最便宜。准确率上四个主要检验都不显著。
- 它很老实地写了：因为表示、提示词、持久化方式一起变，不能说明"修记忆"本身没用。
- 关系：**唯一一篇用小模型、并且认真算了"维护记忆"相对"重读原文"总成本的**。它给"让便宜模型维护状态"泼了冷水：记录不长时，维护不如重读。我们如果走"便宜维护者"，必须和"按来源重读"这个基线比总成本。

## 15. Invalidation Contracts（2609.00243，南达科他州立、西门子，2026-08-31）
- 智能体把 API 报错后的修复办法缓存下来，服务端数据变了以后这些缓存会悄悄失效。办法是让服务端在每条修复建议上带版本戳和可缓存提示，客户端据此精确淘汰。
- 七个模型（含 Claude Haiku 4.5、gpt-5-mini），约 9400 轮。版本戳的判断是确定性的，行级淘汰精度 1.00。一个有意思的现象：同样的字节，Haiku 4.5 首次就照做 100%，Sonnet 5 只有 11% 以下（它不愿加原请求里没有的字段）。
- 关系：失效由数据源自己声明，属于"来源可以机器判定"的一类。多表依赖只实现了没有单独评估。和我们不重合。

## 17. Governance-State Corruption（2610.30698，独立研究者，2026-10-22）
- 研究"哪些记录能进入模型上下文"这层控制信息出错的后果（内容和任务不变，只是元数据错了）。六家模型，2080 对匹配的故障。
- 关系：讲的是记忆治理元数据的完整性，不是依赖更新。相关度低。

## 18. When Stale Constraints Go Unchecked（2608.25553，Glasp，单作者，2026-08-26）
- 设定：整理过的记忆里写着一条决策约束，它的来源记录后来被另一条撤回了。来历链接是在的，但智能体的核查预算有限（比如六条记忆只能查两条）。
- 结果：十六个模型很少去复查一条"读起来已经定了"的约束，大约五次里只有一次去看它的来历；约束被撤回后，77% 的决定仍按旧约束做。强制把一个核查名额给到关键来历，能挽回 61–81 点。一句不指明目标的规则（"优先复查那些对某个方向设了限制的记忆"）能挽回 89 点；只说"注意新鲜度"没有用。
- 模型：Claude Opus 5、Sonnet 5、Haiku 4.5、GPT-5.6 各档、Gemini 3.7、DeepSeek V4、Qwen3.8 等。强弱都有。
- 它自己写的限制：**"这里没有任何东西说明约束在真实部署里多常过时"**；过时状态是作者写的。
- 关系：再一次说明瓶颈在"想不到去查"，不在"查了不会用"。也再一次有人明说缺真实数据里的普遍性。

## 19. AfterDeleteBench（2610.31366，俄亥俄州立，2026-10-22）
- 删掉一条原始记忆后，由它派生出来的状态（比如摘要）还带着信息。用"接触过再删除"和"从没接触过"的配对智能体来归因。
- 小模型（Qwen2.5-7B、Mistral-7B、Phi-3）。一次提问就能从 Qwen2.5-7B 里问出已删除的秘密，约三分之二的情况成功；完整字符串已经不在、只剩分开存的几个部分时，按公开的组合规则重建的成功率 62–99%。沿来历把所有派生记录一起清掉可以消除。
- 限制：记忆的构造是实验者控制的，不是模型自己决定存什么；目标是合成的精确字符串。
- 关系：删除要沿派生关系传播，和依赖更新是同一个结构（上游没了，下游还在）。

## 20. Can Agents Forget When Asked? / Bemula（2610.18052，清华，2026-10-13）
- 第一个专门测"按用户要求遗忘"的基准。50 段多会话对话，135 个遗忘请求（六类），1742 道题，每段对话有一个不带请求的对照版本。
- 六个主流记忆系统，三个模型（GPT-5.6、DeepSeek-V4.1-Flash、Qwen3-32B）。**没有一个系统端到端通过超过 1.5% 的遗忘请求，多数是 0。**要么信息在简单攻击下还能问出来，要么删得比要求的多得多。
- 限制：对话是合成的；只覆盖对话记忆，没有工具使用。
- 关系：删除这一格不是空白，已经有专门的基准，而且结果说明没解决。

## 21. 三篇讲上下文压缩的
- **ARCBench（2611.03223，阿姆斯特丹自由大学）**：压缩后智能体还守不守操作规则。压缩很少把规则删掉；但规则还在的压缩运行，违规次数是完整历史的 2.6 倍，智能体把后来的请求当成许可或者干脆忽略规则。模型含 Claude Sonnet 5.5、GPT-6 各档、DeepSeek-V4-Flash、GLM-5.3。
- **Compaction Laundering（2610.29869，Pixee）**：安全方向。把对话压平成一个字符串再摘要的做法会丢掉"这句话是谁说的"，攻击者伪造的用户指令能混进摘要变成记忆，五个框架上成功率 87–100%，保留角色类型的四个框架是 0%。和我们关系不大。
- **AutoCompact（2610.02163，新加坡管理大学、南洋理工、哈佛）**：**训练**编程智能体自己决定什么时候压缩、保留哪些工作状态、压缩后怎么继续。先用评审模型纠正过的 1052 条轨迹做监督微调，再用任务成败做强化学习。底座是 Qwen3-Coder-30B。SWE-bench Verified 通过率提高 9.2 个点。
- 关系：ARCBench 说明"信息还在但被改写过之后效果变差"，和我们"摆法影响很大"的发现同方向。AutoCompact 是目前读到的唯一一篇**通过训练来改进状态维护**的，它训练的是压缩时机和保留内容，不是依赖。

## 22. 两篇关于指令文件的
- **Context Rot（2606.09090，新加坡管理大学、海德堡）**：路线图性质的短文。把已有的"文档和代码一致性检查器"用到 356 个仓库（有统计代表性的抽样）的智能体配置文件上，**23.0% 的仓库有过时的代码元素引用**。只做检测，没有跑智能体。
- **Stale Instruction Files Override the Code（2610.30571，佐治亚理工、科罗拉多）**：40 个自建项目，指令文件要求的写法和现有代码不一致。不加干预时 **90.1% 的选择照过时的指令做**；Claude Code 在 80 次里 79 次指出了冲突，仍然照做。在用户级指令里加一句"以现有代码为准"，照代码做的比例从 4.2% 升到 91.4%。模型是 Opus 5.5、Sonnet 5.5、GPT-6 Sol。它的解释：指令文件以"指令"的身份进入模型，代码以"工具输出"的身份进入，模型被训练成后者优先级更低。

## 23. 其余四篇
- **SciValidityBench（2610.34767，清华、中科大）**：科研智能体的"记对了但不能用"（比如同一个检验结果，事先定好的才算验证，事后挑出来的只算探索）。把分散的历史编译成显式的"决定性状态"再给读者。四个开源小模型上，编译后的状态比通用事件图高 9–19 点（Qwen3-14B +19，Gemma-3-12B +18，Mistral-7B +11，Phi-3.5-mini +9）；只靠检索得不到这个提升；内容相同时换一种排版没有差别，提升来自"把后果写出来"。**这是我们阶梯之外，另一条"写入时把后果算好，小读者就能用"的证据。**
- **Commitment Hierarchies（2609.37453，佐治亚理工，单作者）**：用户中途改主意时，已经算好的子结果哪些留、哪些改、哪些扔。**让模型逐个节点判断不可靠；让模型只对"这次改动是什么"分类一次，再由确定性程序沿依赖传播，三个模型都达到最优。**gpt-4o-mini：逐节点 0.00，分类一次加程序传播 1.00。还证明了只看局部的策略不可能既安全又省。限制里写了"执行器没记录的潜在依赖"处理不了，合成环境"只说明存在，不说明普遍"。
- **Accept Changes, Reject Attacks（2610.41056，印第安纳大学等）**：把"过时记忆"和"记忆投毒"放在一起，因为两者要求相反的写入决定。**微调一个小的记忆管理器**（Qwen3-4B、Qwen3.5-4B / 9B 等），训练数据围绕一段对话合成，插入明说和暗示的变化以及攻击。过时类的测试集来自 STALE。三个底座上各类分数都提高，总分是未微调的两倍多，"仍不完整"。具体数字没读。**这是目前读到的最接近"便宜的、训练过的维护者"的一篇**，场景是聊天，处理的是事实本身的变化（含暗示的），不是依赖传播。
- **Are We Ready For An Agent-Native Memory System?（2606.24775，上海交大等）**：从数据管理角度评测 12 个记忆系统的综述式实验。只读了摘要，没有提取到具体结论。

## 二、跨场景反复出现的六件事

1. **读一份维护好的状态很容易，从历史里重建很难，对所有档次的模型都一样。**（When Context Changes 40/40 对 9–18/40；Take It From Here 0/312；MemDerive 96% 对 30–58%；SciValidityBench；我们的阶梯。）
2. **提醒一句不够，要把过时的内容本身换掉。**（我们 8B：标记 +4 到 +6，改写 +59；Concord 顶级模型：提醒 26/40，原地改 40/40；Stale Constraints："注意新鲜度"没用；Xu & Wu：79/80 次看见了冲突仍照做。）
3. **依赖一旦被记下来，传播可以交给程序，不需要模型。**（Tether、MemTX、PLANFENCE、Commitment Hierarchies、Stashbird 都是这样。）
4. **让模型做一件窄的事再由程序接手，便宜模型就够用。**（Commitment Hierarchies：gpt-4o-mini 逐节点 0.00，分类一次 1.00；Tether 只加一个字段。）反过来，让模型维护完整状态，顶级模型也不行（0/312）。
5. **难点从"推理"移到了"发现"。**该查的不去查（Stale Constraints 五次里一次）；顺口提到的变化被漏记（Tether，35B 写入者漏 22%）；提醒了不重读（Concord）。
6. **真实世界里多常见，没人知道，而且好几篇自己这么写。**（Stale Constraints、Commitment Hierarchies 的限制；StateWise 只审了 100 段；Context Rot 的 23% 只是指令文件里的代码引用。）

## 三、被几篇同时留作"以后的工作"的空白

- **没有明说、要推断的依赖**：Tether（"需要写入者推断的依赖没有测"）、PLANFENCE、MemTX（没声明来历就全部失败）、Commitment Hierarchies（"潜在依赖"）、Concord（派生的摘要和决定）。只有 TRACE 和 STALE 一类在读取时用模型去核对暗示的失效，中等模型离开久了只有 43%。
- **真实数据里的普遍程度，按类型分**：见上面第 6 条。
- **强主模型加便宜维护者的分工**：读完全部也没有看到。最接近的是 Accept Changes（微调 4B 管理器，聊天，管事实变化不管依赖）和 Commitment Hierarchies（窄角色加程序传播）。
- **失效题（上游变了、没有新值、该说不知道）**：Tether 用"撤回成未确定"处理了结论类的记忆；对带值的记忆（MEME 的失效题）没有人这么做过。

## 四、我们能填的（我的判断，没有经过用户确认）

按"和我们已有的东西接得上、而且本机就能做"排序：

1. **把"撤回"搬到带值的记忆上，解决失效题。**我们量到的失效题上限低（完美写入加思考也只有 28–68），但那几种写法都把旧值留在读者面前。Tether 和 Concord 的做法是把过时的内容从读者眼前拿掉。预测：把过时条目的值直接换成"未确定"，小读者不思考也能答"不知道"。这是一组本机一两小时的实验，结果不管正反都有信息。
2. **窄角色的便宜写入者。**不让 8B 维护整个状态（那条路我们试过，0–2/10），只让它做两件事：记下"谁依赖谁"，记下"发生了变化"。改写和挑选交给程序。用我们的阶梯当尺子，看能到哪一级。这同时回答 Tether 没回答的两点：带值和规则的级联；写入者和读者分开。
3. **真实数据的计数做扎实。**我们已有一份初步的（17%，单人标注）。SWE-chat 全量在手边，StateWise 只审了 100 段且不按依赖分。花费估计 100–250 美元。风险是单独成文偏薄，但可以作为前两条的动机。
4. **不明说的依赖**是最大的空白，但也最难：没有现成的带标注的数据（MEME 的依赖是明说的）。可以从第 3 条的真实数据里挑出来做一个小测试集。这是远一点的事。

**不建议做的**：再做一个依赖感知的记忆机制（Tether、StateGraph、PACMI、MemTX 已经占了）；再做一个诊断基准（MemDerive、MEME、STALE 已经占了）；上下文内的更新失败机制（伯克利那篇做了）。
